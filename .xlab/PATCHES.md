# Carried patches

Everything `xlab` carries on top of its upstream release. One row per change;
remove a row when upstream ships the change and the intake merge replaces ours.

Base: upstream [`v2026.1117.0`](https://github.com/paperclipai/paperclip/releases/tag/v2026.1117.0).

| Change | Branch | Why we carry it | Upstream status |

Adds a controller-enforced shutdown deadline so orphaned sandboxes are reaped | Not yet offered |
| Native sandbox sync uses the realized directory | `fix/sandbox-sync-remote-cwd` ([#6](https://github.com/applyinnovations/paperclip/pull/6)), `fix/sandbox-test-lease-remote-cwd` ([#39](https://github.com/applyinnovations/paperclip/pull/39)) | Native file sync reads `remoteCwd` from the lease; without this a fresh or resumed lease can carry a stale sync root, and an environment Test lease carries none, so the Test's asset upload (the managed Claude config) fails on the Kubernetes provider | Not yet offered |
| Static OIDC sign-in with explicit account linking | `feat/configurable-oidc-xlab` ([#7](https://github.com/applyinnovations/paperclip/pull/7)), `fix/oidc-link-return-path` ([#11](https://github.com/applyinnovations/paperclip/pull/11)) | Keycloak SSO for paperclip.xlab.now. | Claude subscription OAuth for environment drivers | `fix/claude-oauth-sandbox-passthrough` ([#2](https://github.com/applyinnovations/paperclip/pull/2)) | Sandboxed Claude agents authenticate with the shared `CLAUDE_CODE_OAUTH_TOKEN` | Not yet offered |
| Server env never reaches remote targets; Kubernetes exec env over stdin | `security/remote-env-leak` ([#40](https://github.com/applyinnovations/paperclip/pull/40)) | Security fix. Adapters built remote command checks, installs and probes from `{ ...process.env, ...adapterEnv }`, so the server's secrets (database URL, auth and signing secrets, provider tokens) reached sandbox pods, and the Kubernetes provider put every env value into the exec argv, which the kube-apiserver audit log records. `sanitizeRemoteExecutionEnv` now drops server-valued entries on every remote branch, the server applies it again where it dispatches remote environment commands, adapters use `adapterExecutionTargetCommandEnv`, and the Kubernetes provider sends env on stdin | Reported privately upstream: [GHSA-v726-396j-x5vm](https://github.com/paperclipai/paperclip/security/advisories/GHSA-v726-396j-x5vm) (2026-11-23); PR to follow once the advisory is triaged |
| GitHub App installation credentials | `feat/github-app-installation-credentials` ([#3](https://github.com/applyinnovations/paperclip/pull/3)) | Agents clone, push and open PRs as `paperclip-xlab-now[bot]` with one-hour tokens; no personal tokens | Not yet offered |
| Per-company GitHub Apps (`PAPERCLIP_GITHUB_APPS_FILE`) | `feat/per-company-github-apps` ([#18](https://github.com/applyinnovations/paperclip/pull/18)) | Each company (Apply Innovations, The Calile, Playable, KinesisLabs) gets its own App, bot identity and repository access, so Git rulesets can tell companies apart. Adds the `github.app.token` and `github.app.webhooks.verify` plugin capabilities for the forthcoming GitHub plugin. Extends the row above | Not yet offered |
| Run-scoped MCP servers (`PAPERCLIP_RUN_MCP_SERVERS_FILE`, `/api/run-mcp/<name>`) | `feat/run-mcp-server-tokens` ([#22](https://github.com/applyinnovations/paperclip/pull/22)) | Allowlisted agents query xlab Grafana (logs and metrics) through a server proxy authenticated by the run JWT; the server holds the Keycloak client and refreshes its token, so access lasts exactly the run | Not yet offered |
| Extra sandbox providers under forced Kubernetes execution (`PAPERCLIP_EXECUTION_ALLOWED_SANDBOX_PROVIDERS`) and self-hosted plugin selection (`PAPERCLIP_PLUGIN_AUTO_INSTALL`) | `feat/mac-lanes-sandbox-provider` ([#29](https://github.com/applyinnovations/paperclip/pull/29)) | Agents may select a mac-lanes environment (persistent macOS sessions) while Kubernetes stays the default and local/ssh stay refused; the operator selects the image's distribution plugins declaratively because plugin management is hidden on paperclip.xlab.now | Not yet offered |
| Login PTY for the Kubernetes provider (`supportsLoginPty`) | `feat/kubernetes-login-pty` ([#38](https://github.com/applyinnovations/paperclip/pull/38)) | Per-company Claude (`claude setup-token`) and ChatGPT (`codex login --device-auth`) subscription connections are signed in on a terminal exec in the company's tenant Sandbox pod, never in the server. Honours the login lease deadline (`requestedExpiresAt` → Sandbox `shutdownTime` and attested `expiresAt`); adds per-adapter `loginAllowFqdns` for cilium egress. Builds on the `v1beta1` row's `shutdownTime` | Upstream PR text prepared, not yet offered |
| Kubernetes exec keeps a sandbox-built PATH | `fix/kubernetes-exec-path` | The provider dropped every caller `PATH`, so the GitHub operation launchers (which the run puts first on a sandbox-derived PATH) never reached the agent's shell, and `git`/`gh` ran without the company App's credentials. Now only the orchestrator's own PATH is dropped; any other is prepended to the image's PATH | Not yet offered |
| Re-import updates the same project and workspaces | `fix/import-project-matching` | A package project with a `slug` that differs from its name's URL key (`slug: calile`, name "The Calile app") never matched the project it created, so every `replace` import added "The Calile app 2", "3", …; and replacing a project created its workspaces again each time. Matching now also tries the name's URL key, and replace updates existing workspaces (by name, then repository URL) | Not yet offered |
| Sandbox lease waits for its pod on a start-up budget (`podStartTimeoutSec`) | `fix/kubernetes-lease-waits-ready` | `execute` waited for the pod inside the command's own timeout, so the 15 s setup Git-context probe failed (`Could not read execution-target Git context`) whenever the node had to pull the runtime image. `acquireLease` now waits for Ready on its own budget (default 300 s) and releases a Sandbox that never gets there | Not yet offered |
| Kubernetes lease release and destroy return a termination receipt | `fix/kubernetes-termination-receipts` | The provider returned nothing from release/destroy, so a cancelled run's lease never carried a termination receipt and pausing or terminating that agent could never complete (`pausing` forever). It now returns `destroyed` once the Foreground-deleted workload and its pod are confirmed gone, and no receipt if they are still terminating, so the host retries | Not yet offered |
